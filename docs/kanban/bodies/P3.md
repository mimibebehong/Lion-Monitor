# P3 性能（S2 + G14）

## 目标
24 万行指标值规模下，工作台 / 健康树 / 趋势页不再卡死。

## 依据
- `docs/reviews/2026-10-31-总体复查.md` 问题 S2（24 万行首页 34.6 s、健康树 8.7 s）、G14（趋势页一次拉全量、无分页/抽稀，20 000 行 707.9 ms / 7.6 MiB）
- 拍板口径 Q6 = **趋势默认最近 30 天 + min/max 抽稀到 2 000 点，导出 CSV 给全量**（方案 §14.1）

## 要做的事
1. **SQL 聚合**：工作台/健康树取「最新值、计数、越限数」改为 SQL 聚合（`GROUP BY` + 窗口/子查询），不要 Python 端全量拉取再遍历。
2. **去掉 `path_nodes` 的 N+1 查询**：树页一次性取全树（或递归 CTE / 一次 `IN` 查询），杜绝按节点逐个查。
3. **复合索引**：按实际查询模式补索引（如 `(task_id, node_id, metric_code, computed_at)`、`(channel_id, metric_code)`），
   迁移要在带索引的老库上可执行（注意 SQLite 重建表的索引顺序，参考 `e9d79f4` 的教训）。
4. **趋势页**：默认时间窗最近 30 天；超过 2 000 点按 min/max 抽稀（与波形页 `decimate_indices` 同思路，避免尖峰被跳过）；
   CSV 导出始终全量原始点。
5. 加一个可复跑的性能基准脚本（如 `scripts/bench_pages.py`），造 24 万行数据并打印各页耗时，供回归对比。

## 验收标准（必须实测，给出数字）
- 造 **24 万行**指标值数据：
  - 工作台首页 **< 1.5 s**
  - 健康树 **< 1 s**
  - 趋势页 **< 300 ms**（默认 30 天窗 + 抽稀）
- 趋势页抽稀后图上点数 ≤ 2 000，但导出 CSV 行数 = 全量。
- 带索引的老库跑 `init_db` 迁移不报 `database table is locked`（补一个迁移用例）。
- 全量 `pytest` 全绿。

1. **先写测试跑红，再实现跑绿**（TDD）。新增/修改行为必须有对应用例；不许先写实现再补测试。
2. **结果以真实执行为准**：必须实际跑 `pytest tests`、必须实际起页面看效果，不许口头声称通过。
3. 完成后 `ruff format` + `ruff check`（全仓必须 All checks passed）+ 全量 `pytest`，然后 `git commit`。
4. **不扩大范围**：只做本卡片列的事；顺手发现的其它问题写进卡片评论，不动代码。
5. **发现工作区有别的会话/代理的未提交改动** → 立即停手，`kanban block` 并说明，不许强行提交别人的改动。

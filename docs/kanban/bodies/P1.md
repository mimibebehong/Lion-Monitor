# P1 批次事务与状态（B2 + S5）

## 目标
让「一次导入」成为**原子操作**，并让批次状态能回答「这批到底能不能用」。

## 依据
- `docs/reviews/2026-10-31-总体复查.md` §4.1 事务边界（B2，本轮最硬的缺陷之一）、§4.7 批次状态口径（S5）
- 拍板口径：Q3 = **批次状态要三态**（有效 / 部分有效 / 无效），见方案 §14.1

## 要做的事
1. **事务边界**：store 层写操作改为 `commit → flush`，把「建数据集 + 建通道 + 写指标值 + 落状态」包在**一个事务**里；
   计算中途抛异常 → 整体回滚，**库内 0 行新增**（不许留 pending 数据集、不许留半批通道或指标值）。
2. **批次三态**：`dataset.status` 支持 `valid` / `partial`（部分有效）/ `invalid`；1/4 文件损坏或某通道计算失败 → `partial`，
   并在导入结果里点名「哪个通道失败、原因」；全部失败 → `invalid`；全部成功 → `valid`。
3. **页面表现**：`partial` 在数据集列表和导入摘要里显示中文标识（如「部分有效」），不再与「无效」混同；
   值只对成功的通道参与评级（S5 的误导点：现在「部分有效」被标成无效但值照常参与评级）。
4. **回归用例**：至少覆盖「计算中途抛异常 → 0 行新增」「1/4 文件损坏 → partial + 只有 3 个通道有值」「全部失败 → invalid」。

## 验收标准（必须逐条实测）
- 构造一个必然抛异常的计算（如注入坏 scale/坏点数）→ 导入回报一条中文错误，**查库确认 0 行新增**。
- 4 个文件里 1 个损坏 → 数据集状态 `partial`，通道 3 个、指标值只来自这 3 个通道，页面显示「部分有效」。
- 全量 `pytest` 全绿（新增用例覆盖上面三条）。

## 铁律（马哥要求，必须遵守）
1. **先写测试跑红，再实现跑绿**（TDD）。新增/修改行为必须有对应用例；不许先写实现再补测试。
2. **结果以真实执行为准**：必须实际跑 `pytest tests`、必须实际起页面看效果，不许口头声称通过。
3. 完成后 `ruff format` + `ruff check`（全仓必须 All checks passed）+ 全量 `pytest`，然后 `git commit`。
4. **不扩大范围**：只做本卡片列的事；顺手发现的其它问题写进卡片评论，不动代码。
5. **发现工作区有别的会话/代理的未提交改动** → 立即停手，`kanban block` 并说明，不许强行提交别人的改动。
6. 页面实测只用 `bash scripts/dev_serve.sh 8599`（幂等，会自己停旧进程），用 `browser_exec` 访问 `http://127.0.0.1:8599`；
   不要自己 `streamlit run`、不要 `pkill -f`（会被安全策略拦）。`pytest tests` 全量约 65 秒，别重复跑。
7. 决策口径以 `docs/plans/2026-10-28-监测软件方案与UI设计.md` 为准，尤其是 §14（Q1–Q9 拍板口径）；有冲突先停手问。

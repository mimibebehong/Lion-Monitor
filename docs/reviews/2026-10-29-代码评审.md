## P0 — 建议立即修（会误导用户或让配置失效）

### P0-1 三个页面仍是示例数据，且与真实库值冲突

| 页面 | 状态 |
|---|---|
| 工作台 `home.py` | 仍读 `demo_data`（树、指标、设备使用、步骤状态全假） |
| 数据分析 `channel_analysis.py` | 波形 / 频谱 / 包络谱全部来自 `demo_data.spectrum()` 等合成函数 |
| 回收站 `recycle_bin.py` | 仍读 `demo_data.RECYCLE_ITEMS`，看不到真实软删记录 |

**证据**：`home.py:116` 硬编码「CH2 v_RMS 32.49 mm/s（隔膜过辊轴承），已超 alert 4.50」；
而库里真实值（16:10:44 那次采集）是 **10.527 mm/s**。同一系统两个数字，容易被当成事实引用。

**建议**：工作台改读 `metric_value` 最新值 + `metric_limit` 判定；回收站改读各表 `deleted_at`；
数据分析页先接真实波形（`read_vibration`），频谱/包络谱留到 P2 再接。

### P0-2 指标配置里的计算参数不生效

`metric_def.params_json` 支持存 `{"band": [10, 1000]}`，但计算端 `features/metrics.py` 把带宽
写死在 `VELOCITY_BAND = (10.0, 1000.0)`，**用户在「指标配置」改参数不会改变计算结果**。

**建议**：`compute_metrics(samples, fs, params=None)` 接收参数，`pipeline.import_batch` 从
`metric_def` 读参数传入；带宽变化在测试里断言（例如改成 5–500 Hz 后 v_RMS 应下降）。

### P0-3 指标值存在两套删除语义

| 位置 | 行为 |
|---|---|
| `store/metrics.upsert_values` | **硬删**（`DELETE FROM metric_value`）后重插 |
| `store/metrics.delete_values_for_channel` | 软删（写 `deleted_at`） |
| `features/pipeline.purge_dataset` | 调上面两者删除数据集时连带删指标 |

同一张表混用两种删除，后果是：数据集删除后 `metric_value` 被硬删，**回收站无法恢复趋势数据**，
与「全表软删、可恢复」的既定约定冲突。

**建议**：统一为软删；`upsert` 改为「先软删旧点再插新点」，或在 `metric_value` 上加
`UNIQUE(channel_id, code, computed_at)` 用 upsert 语义（表上已有该唯一约束）。

## P1 — 一致性与可维护性

### P1-1 死代码：`store/thresholds.py`

67 行，0 处引用（阈值职责已由 `store/limits.py` 承担）。建议删除，避免后来者改错文件。

### P1-2 指标常量三份重复

| 位置 | 常量 |
|---|---|
| `store/metric_def.py` | `DEFAULT_METRICS` |
| `store/metric_assign.py` | `METRIC_CODES` |
| `features/metrics.py` | `METRIC_UNITS` |

三处内容完全一致（`v_RMS/a_Peak/a_RMS` + 单位）。加一个指标要改三处，必错。
**建议**：`metric_def.DEFAULT_METRICS` 作为唯一来源，其余两处 import 引用。

### P1-3 数据集删除的级联不在那一层

`datasets.delete_dataset` 只软删数据集 + 通道，不碰 `metric_value`；只有 `pipeline.purge_dataset`
做了连带。任何绕过 pipeline 的调用都会留下孤儿指标点（趋势里可能出现无主数据）。
**建议**：把级联下沉到 `delete_dataset`，pipeline 只做编排。

### P1-4 数据接入页硬编码本机路径

`ingest.py:19` 写死 `DEFAULT_DIR = /mnt/d/hermes_wp/Project/…`。换机器/换盘符即失效。
**建议**：进 `lion_monitor/config.py`，用环境变量覆盖。

### P1-5 台账改名不会同步到健康树节点

健康树节点的 `name` 是**装配时的快照**，台账（`monitor_object` / `channel_reg` / `metric_def`）改名后，
树里仍是旧名，两处会不一致。当前只有「悬空引用」检测（台账删除），没有「名称漂移」检测。
**建议**：二选一——
(a) 树渲染时以台账名为准（`ref_id` 存在则显示台账名）；
(b) 台账改名时级联更新引用节点的 `name`。
推荐 (a)，与「健康树只做装配」的定位一致。

## P2 — 工程改进

1. **双轨树实现**：`app/tree_store.py`（假树）+ `app/tree_ui.py`（渲染）+ `store/tree.py`（真数据）三处并存。
   `tree_ui` 仍被健康树页用于渲染，但 `tree_store` 是否还有人用需确认后清理。
2. **阈值表用文本列而非数字列**：因为 Streamlit `st.data_editor` 把 NaN 渲染成 `"None"`（实测），
   改用 TextColumn 后未设阈值显示空白，代价是失去数值控件与即时校验（校验改在保存时做）。
   属已知取舍，建议在方案文档 9.8 补一句说明。
3. **无 E2E 测试**：168 个用例全是单元测试（store / features / 读取层）。页面状态机
   （阈值未保存拦截、两态右栏、导入失败回滚）只能靠手点验证。建议用 `streamlit.testing.v1.AppTest`
   覆盖这三处，避免以后改页面时回归。
4. **BENCH**：单次导入 3 批次 12 文件（每个 64 万点）耗时约 8–10 s，全部在页面线程里同步执行；
   批次多了会卡 UI。后续可加进度条或后台任务。

## 安全

- 静态扫描（今日新增行）：**无命中**（无硬编码密钥、无 `eval/exec`、无 `shell=True`、无 `pickle.loads`）
- SQL：全部走 SQLAlchemy 参数化，无字符串拼接 SQL
- 路径：`数据接入` 的目录来自用户输入，但只用于**读取**（`scan_vibration_dir` 只读头部），
  无写/删文件操作；未验证符号链接跟随（低风险）

  若要多人访问需改成 `enableCORS=true` + `corsAllowedOrigins` 白名单

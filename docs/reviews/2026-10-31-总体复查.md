## 0. 一句话结论

**算法与页面本身是能用的（数值可交叉验证、12 页 0 异常、空态引导完整）；但「导入链路」和「多对象/大数据量」两条主线还扛不住现场长期运行**：同一天第二个任务导不进去、一次失败会留下半批数据、一个 NaN 样本能把页面打成红屏、同通道多节点会串值、24 万行指标值时首页要 34.6 秒。

### 1.2 现在不能上线的部分（阻塞）

| # | 一句话 | 触发条件 |
| --- | --- | --- |
| **B1** | 同一天**第二个任务**导入必失败（`UNIQUE constraint failed: dataset.code`）；4 个 tab 并发导入 2/4 失败 | 现场有 2 个测试任务、或两人两 tab 同时导入 |

### 1.3 上线必须附带的运行约束（在修好之前）

1. **一个任务干到底**（不要在同一天建第二个任务做导入）；不要两个浏览器 tab 同时导入。
2. **同一通道号只挂一个监测对象**（否则趋势/评级/超限计数会串值，见 S1）。
3. **指标值总量控制在几万行以内**（24 万行时工作台 34.6 s，健康树 8.7 s，见 S2）。
4. **不要做「模板整树替换」和「删节点」**——这两类操作不可撤销、回收站里看不到（见 G6）。

## 3. 按维度分节

### 维度 1：数据模型与迁移

**结论：迁移本身是安全的（幂等、不丢数据、有恢复分支），但「历史行 node_id=NULL」的兜底只是「读得出来」，不是「读得对」；旧模型仍在两处页面并用地活着。**

#### 1.1 表结构一致性：`node_id` 的历史行兜底

证据（`…review-model.txt` §P4）：

```
【迁移前】metric_value … CONSTRAINT uq_metric_value_point UNIQUE (channel_id, code, computed_at)
副本迁移前：{'metric_value': 48, 'metric_limit': 2, 'task_node': 22, 'dataset': 4, 'channel': 16}
第 1/2/3 次 init_db 后：metric_value 48 · node_id 为空 48
迁移前后各表行数一致：True
按通道号读到的历史行（node_id IS NULL）共 27 行：读取路径不报错、返回 node_id=None
```

- ✅ 兜底存在：`store/metrics.py::list_values` 按「任务 + 通道号 + 指标码」查，不依赖 `node_id`，历史行照常返回（`node_id=None`）。
- ⚠️ 但「兜底」的语义是**按通道号混读**——这正是 S1 的根因。历史行永远不会被升级成「按节点」口径：`node_id` 一旦为 NULL，它在这套模型里就再也无法归属到具体节点，只能靠通道号猜。
- ⚠️ `data/lion.db` 当前**仍是迁移前结构**（无 `node_id` 列），现场第一次启动 Streamlit 时会跑一次重建迁移。迁移已验证安全，但这是一次「首启即改表」的操作，现场没人守着时出错没人知道（建议 S 级：启动前自动备份一份）。

#### 1.2 旧模型残留：双源与漂移

证据（`…review-model.txt` §P8）：

```
台账（object_registry）对象数 1：['只在台账里的对象']
旧模型（objects.list_objects，读 task_node）对象数 0：[]
树里补一个 component（不挂台账）后：台账 1 条 / 旧模型 1 条
```

- `app/pages/thresholds.py:43` 用 `objects.list_objects(session, task.id)`（读 `task_node`），而「监测对象」页写的是 `monitor_object` 台账 → **同一个任务，两个页面的「监测对象」列表可以不一样**。
- 存量盘点 b.4/b.5 已列「旧模型未彻底退役」，本轮量化了影响面：**阈值页是唯一还在用旧模型的业务页面**；`objects.py` 其余函数无调用方，`thresholds.py`（旧表）无人读（见 G5）。
- 双写风险：目前**没有双写**（写入只走台账/树各一处），风险是「读的口径不一致」而不是「写坏数据」。

#### 1.3 唯一约束与索引是否覆盖新查询

证据（`…review-model.txt` §P1/P2/P3）：

```
metric_value 索引 5 个：ix_metric_value_channel_id / ix_metric_value_node_id / ix_metric_value_computed_at /
                       ix_metric_value_code / UNIQUE(channel_id, code, computed_at, node_id)
metric_limit  索引 4 个：… UNIQUE(node_id/metric_code/deleted_at)
同一 (node_id, metric_code) 连续插入 2 次：metric_limit 成功 2/2 次，表内现有 2 行
同一 (node_id, metric_code) 连续插入 2 次：metric_assign 成功 2/2 次
```

- ✅ `metric_value` 的新唯一键 `(channel_id, code, computed_at, node_id)` 正确覆盖「同通道多节点同刻各存一行」。
- ❌ `metric_assign` / `metric_limit` 的唯一约束**在 SQLite 下对生效行不生效**：约束包含 `deleted_at`，而 NULL 在唯一索引里互不相等 → 可以插入两条完全相同的有效行（实测 2/2 成功）。唯一性只剩代码里的 `exists` 查询。`pipeline.metric_jobs` 用 `{(node_id, code): row}` 字典，重复行会静默取最后一条（G3）。
- ⚠️ 索引对查询「够用但不优」：趋势查询走 `ix_metric_value_code` 再 `USE TEMP B-TREE FOR ORDER BY`（即先按 code 全表扫，再内存排序），没有 `(channel_id, code, computed_at)` 复合索引；最新值查询走 `ix_metric_value_channel_id` + 临时 B 树排序。行数一上来就是 S2 的一部分原因。

#### 1.4 迁移幂等 / 中断恢复

证据（`…review-model.txt` §P4/P5）：连续 3 次 `init_db` 行数与结构完全一致；造 5 行数据后模拟 `metric_value_old` 残留，再 `init_db` → `metric_value` 5 行、残留 `_old` 表 0 个。

- ✅ 幂等、可重复执行、重建失败有「`*_old` 搬回」恢复分支（与技能里踩坑记录一致）。
- ⚠️ 迁移只在 `init_db()` 里跑；没有版本号表（`schema_version`），无法知道某个库停在哪一步，也无法「只跑一次」防重。

### 维度 2：计算正确性

**结论：三个内置指标的数值是对的（合成正弦逐位吻合），但口径有 4 处未文档化的隐藏假设；`window_s / step_s / window_fn` 三个参数是「假参数」——schema 里有、页面能改、计算里完全不读。**

#### 2.1 指标定义与实现是否一致

| 指标 | 定义 | 实现 | 单位 | 一致性 |
| --- | --- | --- | --- | --- |
| `a_Peak` | 峰值加速度 | `max(abs(x - mean(x)))`（detrend=True 时） | g | ✅ 数值一致，但「去均值后的峰值」≠「绝对峰值」（见 2.1 隐藏假设） |
| `a_RMS` | 加速度有效值 | `sqrt(mean(x²))`（去均值后） | g | ✅ |
| `v_RMS` | 速度有效值 | 带通(4 阶零相位) → 频域积分 `×G_TO_MM_S2/(jω)` → RMS | mm/s | ✅ 合成正弦 6.089070 vs 理论 6.0890（0.00%） |
| 包络谱 | 希尔伯特包络谱 | `features/envelope.py`，带通→希尔伯特→去均值→FFT | g | ✅ 仅页面分析用，不进指标值 |

**隐藏假设（4 处，全部未在页面/方案写明）**：

| # | 假设 | 证据 | 影响 |
| --- | --- | --- | --- |
| H1 | `a_Peak/a_RMS` 是**去均值后**的交流值；`detrend=False` 时变成含直流的绝对值 | 加 0.5 g 直流偏置：`detrend=True` → a_Peak 0.807581 / a_RMS 0.565692；`detrend=False` → **1.306794 / 0.754989**（`…review-compute.txt` §C1） | 现场若有人关掉「去趋势」，a_Peak 会凭空多 0.5 g，且没有任何提示 |
| H2 | `v_RMS` **切掉首尾各 0.5 s**（滤波暂态），20 s 记录实际只用 19 s | 切/不切：6.089070 vs 6.101639（−0.206%），参与计算时长 95.0%（§C6） | 20 s 短记录丢 5% 数据；方案/页面都没写这条 |
| H3 | 带通上限被**静默夹到 `0.95 × fs/2`**（32 kHz 下 15 200 Hz） | `band_high=16000` 与 `30000` 算出的 v_RMS 完全相同（6.089069641）（§C2） | 用户以为按 16 kHz 算的，实际 15.2 kHz |
| H4 | 滤波器固定 4 阶 Butterworth 零相位、频域积分带内掩码 | `features/metrics.py:50` `butter(4, …)`、`:89-101` | 不可配；阶数变化对 v_RMS 有影响但用户无法调 |

#### 2.2 转速门控

证据（`…review-compute.txt` §C4）：

```
v_RMS  字段 ['window_s','step_s','band_low','band_high','window_fn','detrend']  scaling=[None…]  needs_speed=False
a_Peak 字段 ['detrend']                                                          needs_speed=False
a_RMS  字段 ['detrend']                                                          needs_speed=False
resolve_rpm(None,None,None) = (None, None)
```

- ✅ 结论正确：内置三指标都是「绝对值类」，无转速也能算（与方案 3.3 一致）。
- ⚠️ 但**本期没有任何指标真正依赖转速**：`scaling=speed` 只可能出现在自建指标上，而自建指标在本期根本没有计算实现（`_skip_reason` 第二条直接判「本期没有计算实现」）。也就是说「转速门控」目前是**一条空逻辑**——`rpm_used / rpm_source` 永远写 NULL/空串，「无转速时哪些指标被跳过」这个问题在当前版本没有实际发生场景。
- ⚠️ 更实际的风险是**转速存了但不生效**：`tree.node_rpm(depth=3)` 从通道往上只找「通道→对象→设备」，**写在任务根节点上的转速取不到**（实测：根节点填 1480，`node_rpm(通道)=1500.0` 仍是设备那层的值，`…review-params.txt` §T4）。方案 3.2 只说「节点手填」，没写查找深度。
- ✅ 可追溯性：跳过原因写进 `ImportResult.skipped_metrics`，页面上能点名（`…review-ingest.txt` §I2 的字段清单里没有它，但 pipeline 有 `logger.warning` 与页面提示）。

#### 2.3 参数消费清单（哪些真生效）

证据（`…review-compute.txt` §C1，逐个改动看输出是否变化）：

| 参数 | 声明处 | 实测是否影响输出 | 说明 |
| --- | --- | --- | --- |
| `band_low` | `params.py:85-92` | ✅ 生效（400 Hz → v_RMS 6.089→0.000887） | |
| `band_high` | 同上 | ✅ 生效（300 Hz → 6.082151） | 但被夹到 0.95×Nyquist（H3） |
| `detrend` | `params.py` a_Peak/a_RMS/v_RMS | ✅ 生效 | |
| `window_s` | `params.py`（默认 2 s） | ❌ **未消费**（1.0 s 与 2.0 s 输出完全一致） | 页面可改、可以存、可以进 `params_hash`，但计算不读 |
| `step_s` | 同上 | ❌ **未消费** | 同上 |

#### 2.4 降采样 / 抗混叠

证据（`…review-compute.txt` §C5）：

```
输入  8000 Hz → 谱峰  8000.00 Hz
输入 12000 Hz → 谱峰 12000.00 Hz
输入 20000 Hz → 谱峰 12000.00 Hz（理论折叠 12000）
输入 30000 Hz → 谱峰  2000.00 Hz（理论折叠 2000）
```

- ✅ 软件**不引入**混叠：全程用原始采样率做 `rfft`，不做降采样；上屏抽样用 min/max 包络（不改频率轴）。
- ⚠️ 软件也**不检测**混叠：>fs/2 的成分按物理折叠出现在谱上，页面照常当成真实频率显示。32 kHz 下 16 kHz 以上不可信，而现场传感器带宽常见 10 kHz、安装共振可能到 20 kHz+ → 建议在 FFT 页对 `f > 0.45 fs` 加一条固定提示（T5），不要在软件里做抗混叠滤波（会改变 a_Peak/a_RMS 口径）。

#### 2.5 数值边界

证据（`…review-compute.txt` §C3）：

| 场景 | a_Peak | a_RMS | v_RMS | 行为判定 |
| --- | --- | --- | --- | --- |
| 0 点 | — | — | — | ✅ 抛 `ValueError: 样本为空` |
| 1 点 / 10 点 / 63 点 | 0 | 0 | 0 | ⚠️ **静默返回 0，且判为「有效」**（a_rms=0 → 实际会被判「信号近似为零」无效，但 v_RMS 单独看是 0） |
| 64 点（=阈值） | 0.542144 | 0.252349 | 0 | ⚠️ a/v 有值，v_RMS 静默 0（带通不足 64 点后返回 None） |
| 常量 0 | 0 | 0 | 0 | ⚠️ 被判「信号近似为零（传感器未接）」——**这是对的方向**，但恒定 5 g 也被同样判无效（见 G11） |

| 含 Inf | nan | nan | nan | ❌ 同上 |

### 维度 3：参数与阈值体系

**结论：导入计算与页面展示共用同一个函数（一致）；模板导出只带「覆盖 diff」，跨任务导入会静默漂移（S3）。判级已收口到 `limits_rules.grade`，但仍有两份「自己判级」的死代码和一份「播种了但没人读」的旧阈值表。**

#### 3.1 三级继承在「导入计算 / 页面展示 / 模板导出」三处

证据（`…review-params.txt` §T1）：

```
A 节点（定义默认 1000，节点覆盖 2000）：
  导入计算（metric_jobs）生效参数 band_high=2000.0  指纹 …
  页面展示（effective_params）: 2000.0
  模板导出：params={'band_high': 2000.0} locked=False（导出的是节点覆盖项，不是生效参数）

C 节点（定义默认 1000，无覆盖）：导入计算 band_high=1000.0；模板导出 params={}（空）
把 C 的模板导入 B（B 的定义默认是 500）：
  导入后 B 节点生效参数 band_high=500.0 → ★ 由 1000 静默变成 500
```

| 位置 | 用的函数 | 结果 |
| --- | --- | --- |
| 导入计算 | `metric_assign.compose_params`（`pipeline.metric_jobs`） | 生效值（含定义默认 + 节点覆盖 + 锁定快照） |
| 页面展示 | `metric_assign.effective_params` | 与上面**同一个函数**，一致 ✅ |
| 模板导出 | `tree_template._export_metric` → `params_json` 原样 | 只带「覆盖 diff」，**不带定义默认** ❌ |

→ **S3**：跨任务导入时，「只跟默认」的节点会跟目标任务的默认走。如果目标任务把 `band_high` 从 1000 改成 500，同一模板搬过去后算出来的 `v_RMS` 就变了，而页面上没有任何提示（模板预览只报节点数/绑定数/未匹配）。

#### 3.2 `params_hash` 去重

证据（`…review-params.txt` §T2、`…review-compute.txt` §C2/C7）：

```

1000 与 1000.0 → 同一指纹
band_high=16000 vs 30000：数值相同（都夹到 15200），但 params_hash 不同：82de14b6709d vs 47586af14af3
4 通道同参数导入：真算 12 次 / 复用 0 次（cache 每文件新建，pipeline.py:361）
```

- ✅ **不会把「参数相同但信号不同」的通道误复用**：cache 在 `import_batch` 里按文件新建（`features/pipeline.py:361`），key 是 `(指标码, 参数指纹, 转速)`，生命周期只有一个文件 → 天然按文件隔离。
- ⚠️ 但 hash 输入**只有参数字典**，不含指标码/采样率/通道/数据集；跨文件复用靠「每文件一 cache」这个脆弱约定。一旦有人为了省算力把 cache 提到通道循环外，就会串值——这不是当前缺陷，但是结构性隐患（S6）。
- ⚠️ hash 记的是**用户填的参数**，不是**实际生效参数**：`band_high=30000` 被夹到 15200 但指纹不同 → 用指纹追溯「当时按什么带宽算的」会得出错误结论。

### 维度 4：导入链路与数据完整性

**结论：文件格式校验是严的（长度/头部/时间都会拦），但「拦得住」和「拦得住之后留下的库状态」是两件事；目前几乎所有失败路径都会留下半批数据。**

#### 4.1 事务边界（B2，本轮最硬的缺陷之一）

证据（`…review-compute.txt` §C8，节点参数 `band_low=0` 让计算抛 `ValueError`）：

```

('DS-20261031-001','pending','CH1','pass','')
('DS-20261031-001','pending','CH2','pass','')
('DS-20261031-001','pending','CH3','pending','')
```

根因（代码级）：`app/store_ctx.py:70` 用 `session_scope` 包了整页会话，但**每个 store 函数内部自己 commit**：

```
src/lion_monitor/store/datasets.py:163   create_dataset → commit
src/lion_monitor/store/datasets.py:187   add_file → commit
src/lion_monitor/store/metrics.py:126    upsert values → commit
```

→ 批次级回滚无从谈起：异常发生时，前面几次 commit 已经把「数据集 + 通道 + 半套指标值」写进库。`features/pipeline.py` 里 `commit()` 出现 0 次——事务边界根本不在管线手里。

#### 4.2 文件校验（能读但内容不对）

证据（`…review-ingest.txt` §I1）：

#### 6.1 单批次实测（4 通道 × 20 s @32 kHz）

→ 内存量级健康：同一时刻只有当前通道样本常驻（2.4 MiB/通道），没有「一次读 4 通道」的峰值。

## 4. 问题清单

> 分级：**阻塞**（数据错/必崩/不可用）→ **严重**（结果误导或长期不可用）→ **一般**（可用但有坑）→ **建议**（工程卫生）。
> 「已有」标记表示已有材料已列过，本文只补证据/影响面。

### 4.1 阻塞（3 条）

#### B1 数据集编号撞全局唯一键，第二个任务/并发导入必失败
- **现象**：同一天任务 A 导入 `DS-20261031-001` 成功后，任务 B 导入同一目录 → `IntegrityError: UNIQUE constraint failed: dataset.code`；4 个 tab 并发导入 2/4 失败。
- **证据**：`reports/2026-10-31-review-model.txt` §P6；`…review-perf.txt` §F4；代码 `store/datasets.py:123-127`（`_next_code` 用「本任务条数+1」）、`models.py` `ix_dataset_code` UNIQUE。
- **影响**：现场只要建第二个测试任务（换产品/换工位就会建），当天就导不进去；两人同时操作也导不进去。报错是裸 `IntegrityError`，页面对它不捕获（见 B3）→ 红屏。
- **修法**：编号改全局单调（用 `dataset.id` 或独立 `seq` 表 + `BEGIN IMMEDIATE`），唯一约束改 `(task_id, code)`；或在 `_next_code` 上做冲突重试（最多 3 次）。**0.5 天**。

#### B2 导入没有批次事务，失败必留半批
- **现象**：任一通道计算抛异常 → 数据集（pending）、已处理通道（pass）、已算出的指标值全部留在库里。
- **证据**：`…review-compute.txt` §C8（dataset 1 行 / CH1-CH2 pass / 6 行值）；`…review-ingest.txt` §I1（fs=0、0 点、scale=NaN 后均有残留计数）；代码 `store/datasets.py:163/187`、`store/metrics.py:126` 各自 `commit()`，`features/pipeline.py` 里 `commit()` 0 次。
- **影响**：趋势/评级把半批值当正常值用；用户重导后同一时刻出现重复值风险；库里长期积累「pending 空壳」。
- **修法**：`import_batch` 改为「一个事务边界」——把 store 层的 `commit()` 改为 `flush()`，由 `import_batch` 统一 `commit/rollback`（或在 `session_scope` 里加 `savepoint`）；失败时不保留数据集。**1.5 天**（要改 6 个 store 函数的提交点，回归面大）。

#### B3 未捕获的 `IntegrityError` 会把页面打成 Traceback
- **现象**：`scale=NaN` / 头部 NaN / 同批重复通道号 → 抛 `IntegrityError`；`app/pages/ingest.py:242` 只捕获 `(DatasetError, VibrationFormatError, ValueError)`。
- **证据**：`…review-compute.txt` §C10、`…review-ingest.txt` §I1。
- **影响**：一个坏样本/一次采集重名文件 = 整页红框 + 半批残留（B2 叠加），操作员无法自救。
- **修法**：① `read_vibration` 增加有限性/`fs>0`/`scale` 有限性校验，坏文件降级为 `files_bad`；② 写入前过滤非有限值（或直接判该文件无效）；③ `add_file` 前预检同批通道号重复；④ 页面 except 兜底 `Exception` + 明确文案（不要暴露 SQL）。**0.5 天**。

### 4.2 严重（6 条）

#### S1 同通道多节点混值：趋势锯齿、评级串值、超限翻倍
- **现象**：同一通道号挂两个监测对象时，按通道号取数把两份值混在一起。
- **证据**：`…review-pages.txt` §G3（6 行 / 3 个时点；两节点 latest 同为 10.527；`over_count` 6 vs 应为 3）；代码 `app/pages/trends.py:193`、`features/health.py:69-70`（cache 键 `(通道名, 指标码)`）。
- **影响**：维护人员看趋势看到锯齿；两个对象阈值差 50 倍却都判成同一状态；超限记录重复计数 → 误判「设备劣化加速」。
- **修法**：三处取数加 `node_id`（`list_values(..., node_id=…)`），`series_cache` 键加 `node_id`；CSV 增加「节点」列。**1 天**（含页面回归）。
- **依赖**：是否允许「同通道号多对象」需马哥拍板（Q1）。

#### S2 大数据量下工作台/健康树取数崩塌
- **现象**：24 万行指标值时 `node_health` 8.7 s、`task_overview` **34.6 s**。
- **证据**：`reports/2026-10-31-review-scale.txt`（36 行 137 ms → 1 200 行 325 ms → 24 万行 34 594 ms）。
- **影响**：S4 切窗后单批 20 s 会产出 10 点/指标（步长 2 s），行数 ×10；一年现场数据轻松到几十万行 → 每次打开工作台等半分钟以上，Streamlit 默认超时/用户以为卡死。
- **修法**：① 取最新值用 SQL（`MAX(computed_at)` 子查询或窗口函数），不要拉全量；② `over_count` 用 SQL `COUNT`；③ `path_nodes` 改为一次取全树内存遍历（去掉每节点一次查询）；④ 补 `(channel_id, code, computed_at)`、`(node_id, code, computed_at)` 复合索引。**2~3 天**。

#### S3 模板导出只带覆盖 diff → 跨任务导入静默漂移
- **现象**：源任务 `band_high=1000`（无覆盖）导出的模板 `params={}`；导入到默认 500 的目标任务后生效值变 500。
- **证据**：`…review-params.txt` §T1（`导入后 B 节点生效参数 band_high=500.0 ★ 由 1000 静默变成 500`）；代码 `tree_template.py:168-169`（只导出 `params_json`）。
- **影响**：同一设备模板复制到另一任务后，算出的 v_RMS 变了，页面无提示；现场「照模板建树」是最常见动作。
- **修法**：导出时同时写 `effective_params`（或 `params_default` 快照），导入时按「锁定/覆盖/跟随默认」三态让用户选；预览里显示「N 个指标参数将与目标任务默认不同」。**1 天**。

#### S4 `stale` 只置位不展示（深化已有 G-2）
- **现象**：改参数/转速后历史值 `stale=True`，但趋势、评级、概览全都照常用，无任何标识。
- **证据**：`…review-params.txt` §T4（`[(0.5, True, 'old')]`）；`grep -rn "stale" app/` 仅 1 处注释。
- **影响**：现场调了带宽参数后，看到的还是旧参数算的值；若据此判断「设备恢复了」是错误决策。
- **修法**：趋势点用空心/灰点区分，图注「N 个点由旧参数算出」；评级页提示「待重算 N 条」并给「重算本通道」按钮（重算逻辑可复用 import 的 compute 路径）。**1 天**。

#### S5 「部分有效」被标成「无效」，值却照常参与评级
- **现象**：4 个文件里 1 个损坏 → `status=无效`，但另外 3 个通道的 9 行值已落库并被趋势/评级使用。
- **证据**：`…review-ingest.txt` §I4、`…review-compute.txt` §C9（`status=无效 … 有效指标值行数 9`）；代码 `features/pipeline.py:433-437`（非全 ok 一律「无效」）。
- **影响**：操作员看到「无效」以为这批不能用，实际系统正在用它判断设备健康；状态字段失去可信度。
- **修法**：状态三态（有效 / 部分有效 / 无效）或加 `channel_ok/files_ok` 明细列（`ImportResult` 已有 `files_ok`，只是没进状态）。**0.5 天**。

#### S6 `params_hash` 不含采样率/生效带通，追溯与去重都靠「每文件一 cache」的约定
- **现象**：`band_high=16000` 与 `30000` 被夹到同一 15200、数值相同，但指纹不同；指纹里也没有 fs、指标码、通道。
- **证据**：`…review-compute.txt` §C2/C7；`…review-params.txt` §T2；代码 `params.py:195`、`pipeline.py:361`（cache 每文件新建）。
- **影响**：审计/追溯「这个值按什么参数算的」会得到错误结论；未来把 cache 提到循环外就会串值（结构性隐患，当前不是缺陷）。
- **修法**：指纹输入加入 `code` + `fs` + 生效带通（夹紧后）；或直接把 `effective_params_json` 存到 `metric_value`（更利于审计）。**0.5 天**。

## 5. 必须由马哥拍板的问题（不是 bug，是设计取舍）

| # | 问题 | 为什么必须你定 | 我的推荐 |
| --- | --- | --- | --- |

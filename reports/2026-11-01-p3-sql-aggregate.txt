一、改了什么（口径一行没动）
================================================================================
1. store/metrics.py 新增 SQL 聚合入口（都只发固定几条语句，不随点数增长）：
   - SeriesScope(shannel_node_id, channel_code, code, include_unattributed) —— 一条序列的取数范围
   - SeriesRequest(scope, limit) —— 序列 + 它自己的生效阈值
   - series_stats_batch()  → 计数 / warn 数 / alert 数 / 最新一行
        同一阈值：GROUP BY 计数一条（带条件 SUM 算越限）+ 窗口函数取最新一条 = 2 条 SQL
        阈值不同：计数一条 + 每个阈值一条 + 最新一条
   - series_counts()      → 每条序列行数（九步 ⑨「至少两个点」用，1 条 SQL）
   - over_values() / over_values_for_scopes() → 只取越过 warn 的行（阈值条件下推 SQL）
   - list_values(..., since=) —— 给趋势页 30 天窗口留的入口（Q6，页面接线属 t_873255f7）
   非有限值（±Inf）在 SQL 里就挡掉（value 必须在 ±sys.float_info.max 之间），
   与 limits_rules.grade / features.health.point_level 口径一致：先判 alert，命中即 alert，
   warn_count 只算「越过 warn 未到 alert」。

2. features/health.py：node_health 不再逐节点查祖先链、不再拉整串点
   - 树读一次；阈值用 limits.resolve_limits()（一次取全量阈值行 + 内存沿父链继承）
   - 最新值 / 越限条数走 series_stats_batch（指标节点的父节点就是通道节点，层级固定）
   - 向上汇总按 path 深度倒序（父在子后），不再逐节点 tree.path_nodes

3. features/overview.py：
   - over_records：按生效阈值分组，每组一条 SQL 只取越限行；去重键仍是
     「通道节点 × 指标 × 计算点」（P2 / S1）
   - health_counts / device_overviews 复用 task_overview 里算好的那次 node_health
   - step_states ⑨ 改用 series_counts（不再拉整串点）
   - 返回结构（OverRecord / DeviceOverview / TaskOverview / steps）与页面完全兼容

4. features/series.py：新增 metric_scopes()（纯树结构算范围，不拉值）；
   metric_series() 改为基于它（原实现每个指标节点都要 path_nodes 查一次祖先链）。

5. store/limits.py：list_limits(nodes=) 可复用已读的树；新增 resolve_limits() 批量继承。

四、实际查询模式与建议索引（交给 t_100e6ac4）
================================================================================
表 metric_value 上现在的语句形态（全部经 channel/dataset 三表 JOIN 过滤任务与软删）：

A) 计数 / 越限计数（health.node_health、overview.step_states、series.stats）
   SELECT coalesce(metric_value.node_id, -1) AS node_key,
          channel.code AS channel_code, metric_value.code AS metric_code,
          count(*) AS rows,
          sum(CASE WHEN value 有限 AND value >= :warn  THEN 1 ELSE 0 END) AS warn_hits,
          sum(CASE WHEN value 有限 AND value >= :alert THEN 1 ELSE 0 END) AS alert_hits
     FROM metric_value JOIN channel ON channel.id = metric_value.channel_id
                      JOIN dataset ON dataset.id = channel.dataset_id
    WHERE dataset.task_id = :task AND dataset.deleted_at IS NULL
      AND channel.deleted_at IS NULL AND metric_value.deleted_at IS NULL
      AND metric_value.code IN (:codes)
      AND (metric_value.node_id IN (:node_ids)
           OR (metric_value.node_id IS NULL AND channel.code IN (:legacy_codes)))
    GROUP BY coalesce(metric_value.node_id, -1), channel.code, metric_value.code
   → 建议索引 idx_metric_value_node_code_time ON metric_value(node_id, code, computed_at)
     （覆盖 WHERE 的 node_id IN + code IN，且 computed_at 让 B) 的取最新走索引序）

B) 取每组最新一行（health 的 latest_value / latest_state）
   SELECT ..., row_number() OVER (PARTITION BY coalesce(node_id,-1), channel.code, code
                                  ORDER BY computed_at DESC, id DESC) AS rn ...
     ... 同上 WHERE ... 外层 WHERE rn = 1
   → 同一索引 (node_id, code, computed_at DESC) 可让 PARTITION/ORDER 免排序（SQLite 用索引序）

C) 越限明细（overview.over_records、metrics.over_values）
   SELECT id, channel_id, node_id, channel.code, dataset.id, code, value, unit, computed_at, ...
     FROM metric_value JOIN ... WHERE <同上作用域> AND value 有限 AND value >= :warn
    ORDER BY computed_at, id
   → 选择性来自 value 条件；索引 (node_id, code, computed_at) 可先按作用域收窄，
     再逐行判 value（比全表扫好），ORDER BY 的排序量也从 24 万降到命中行数

D) 趋势取数（trend.list_values，未改）
   ... WHERE dataset.task_id AND channel.code = :code AND metric_value.code = :code
       [AND node_id = :node] [AND computed_at >= :since] ORDER BY computed_at, id
   → 建议 (node_id, code, computed_at) 与 (channel_id, code, computed_at) 两条
     （这条也顺带解决趋势页 <300 ms 的目标；Q6 的 since 参数本卡已加到 store 层）
